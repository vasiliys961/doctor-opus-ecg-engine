## 2. Как устроен анализ изображения

Пользователь на `/ecg` загружает файл. Превью читается в data URL. В запрос уходит:

- `file`
- промпт страницы: `Analyze the ECG image and generate a diagnostic protocol.`
- `clinicalContext`
- `mode`: `fast` | `optimized` | `validated`
- `imageType=ecg`
- `isTwoStage=true`
- `useStreaming` (по умолчанию включён)
- модель режима

Маршрутизация со страницы:

| Режим | Модель, которую ставит страница |
| --- | --- |
| fast | `google/gemini-3.8-flash` |
| optimized | `anthropic/claude-sonnet-5` или `openai/gpt-5.6-sol` |
| validated | `anthropic/claude-opus-5.5` |

Сервер (`/api/analyze/image`) может подменить модель: validated по умолчанию идёт в `MODELS.OPUS_VALIDATED` (`lib/validated-opus-model.ts`, сейчас Opus 5.5, откат через env), для сложного кейса есть предложение Fable. Список разрешённых моделей режется на сервере. Это production routing. В новом проекте нужен свой конфиг, без импорта `lib/openrouter.ts`.

Двухэтапный путь, которым пользуется страница:

1. Gemini Flash (`extractImageJSON`) смотрит картинку и возвращает JSON наблюдателя. Для модальности `ecg` в промпт наблюдателя подставляются `SPECIALIST_CRITERIA.ecg`: калибровка и скорость, ритм, ЧСС, ось, P/PR/QRS/QT/QTc, ST, зубцы, критерии гипертрофии, блокады, плюс список патологий (ACS, ФП, WPW, Brugada, ТЭЛА, электролиты и т.д.). Наблюдателю запрещены диагноз и лечение.
2. Текстовая модель читает JSON и клинический контекст. Потому что страница шлёт `isTwoStage=true`, флаг доходит как `isRadiologyOnly`, и system prompt второго шага — `RADIOLOGY_PROTOCOL_PROMPT` (роль радиолога, RSNA/ACR, HU, BI-RADS). ECG-критерии при этом остаются в user-сообщении через `getDirectivePrompt`.
3. Ответ — свободный markdown, не структурированный объект измерений.
4. Отдельной кнопкой `AnalysisResult` вызывает `/api/protocol/diagnostic-report` с `kind=ecg` и моделью `haiku`. Этот шаг переписывает уже полученный текст в короткий отчёт с фиксированными английскими заголовками: Technical Parameters, Findings, Differential Diagnosis, Clinical Correlation Needed, Impression, Recommendations. Промпт прямо запрещает выдумывать измерения, которых не было в исходном тексте.

`app/api/analyze/ecg/route.ts` в этот поток не входит. Его non-streaming ветка вызывает `analyzeImage` без `imageType`, то есть без ECG-критериев. Для переноса ориентир — страница плюс `/api/analyze/image`, а не этот route.

## 3. Форматы и препроцессинг

Страница ЭКГ принимает то, что браузер считает `image/*`. PDF в `accept` не входит. DICOM на этой странице тоже отключён: дефолт `ImageUpload` включает `.dcm`, но `/ecg` передаёт `accept="image/*"`. PDF обрабатывается в лабораторном и генетическом API, не в ECG-потоке.

Цепочка обычного изображения в `/api/analyze/image`:

1. `ensureVisionSupportedImage` — jpeg/png/gif/webp проходят как есть; остальное (в том числе HEIC) sharp переводит в JPEG quality 90. На macOS есть запасной путь через `sips`.
2. `enhanceMedicalImageBuffer` — normalize + sharpen. По умолчанию выключено (`IMAGE_AUTO_ENHANCE_ENABLED` не `true`).
3. `anonymizeImageBuffer`, если `maskImage` не прислан как `false`. Страница ЭКГ поле `maskImage` не шлёт, на сервере умолчание — маскировать. Чёрные прямоугольники: верх 10% высоты, низ 15%, левый и правый край по 12% ширины.
4. Если буфер больше 4 МБ, `compressImageBuffer` уменьшает сторону и перекодирует в JPEG quality 0.85.

Для ЭКГ шаг 3 опасен: калибровочный импульс, сетка, подписи отведений и края кривой часто лежат именно в этих полях. В новом приложении маску краёв для ECG-изображения нужно делать выключенной по умолчанию и оставлять явную кисть редактора. Авто-sharpen для сетки тоже лучше не включать, пока нет отдельной проверки, что он не сдвигает измерения линейки.

Клинический текст перед моделью проходит `anonymizeText`. На странице есть эвристика «три слова с заглавной буквы» как предупреждение о ФИО. Это UI-подсказка, не гарантия деперсонализации.

## 4. Цифровая линейка

`components/EcgCaliper.tsx` уже есть и встроена в страницу кнопкой Digital Caliper (Ruler).

Что реализовано:

- две точки по изображению, перетаскивание мышью;
- горизонтальная дистанция в пикселях;
- время `round((dx / calibration) * 1000)` при ручном масштабе px/сек (ползунок 50…1000, старт 100);
- переключатель скорости 25 / 50 мм/с на экране;
- подсказка калибровать по сетке: 1 с = 5 больших клеток при 25 мм/с.

Чего нет, хотя ТЗ это перечисляет:

- напряжение / амплитуда в мВ или мм;
- использование скорости 25/50 в формуле (состояние `speed` на расчёт не влияет);
- автоматическое чтение сетки;
- вертикальная компонента (берётся только `|x2-x1|`);
- touch-жесты, в коде только mouse events.

Переносить компонент стоит вместе с этими ограничениями, подписанными в UI, и уже в новом репозитории добавлять напряжение и привязку к скорости.

## 5. Редактор

`ImageEditor` — кисть, которая закрашивает область чёрным и сохраняет JPEG quality 0.85. На странице ЭКГ кнопка «redact». После сохранения data URL снова становится `File` и уходит в анализ вместо исходника. Это и есть redaction/editor из ТЗ. Отдельного ECG-редактора кривой нет.

## 6. Измерения, качество, fusion

Единого объекта `{heart_rate, rhythm, pr_ms, qrs_ms, qt_ms, qtc_ms, axis}` нет. Числа живут внутри текста модели. Signal quality как отдельный движок для изображения тоже нет: в JSON наблюдателя есть поля `image_quality` и `quality_issues`, дальше они растворяются в прозе.

Evidence fusion между сетью 531 и vision отсутствует, потому что сети 531 в Doctor Opus нет. Рассуждение — это второй LLM-шаг плюс опциональное переписывание в диагностический отчёт. Противоречие каналов сохранять негде: канал один.

Ссылки после ответа (`lib/ecg-reference-links.ts`) ищут в тексте ключевые слова STEMI, ФП, трепетание, ЖТ, LBBB, RBBB, AV-block, long QT и строят поисковые URL LITFL и ECGWaves. Это не клинический вывод.

## 7. USB-ЭКГ

`SerialDeviceManager` на `/devices` читает Web Serial как текстовые числа построчно, рисует последние 100 точек на canvas (ожидаемый диапазон 0–1024, одна кривая) и по кнопке отправляет PNG этой канвы в `/api/analyze/image` с `imageType=ecg`. Частота дискретизации, 12 отведений и файл сигнала не формируются. Для raw-пайплайна нового движка этот модуль не является парсером. Имеет смысл переносить его только как отдельный экспериментальный захват картинки, с явной пометкой ограничений.

## 8. Что забирать в новый репозиторий

Имеет смысл копировать и адаптировать, с записью в `docs/SOURCE_PROVENANCE.md`:

- поток страницы `/ecg`: загрузка, превью, режимы, streaming-отображение текста;
- `EcgCaliper.tsx`;
- `ImageEditor.tsx` как ручная редактура;
- ECG-блок `SPECIALIST_CRITERIA` и наблюдательский JSON-промпт для модальности `ecg`;
- `DIAGNOSTIC_ECG_SYSTEM_PROMPT`, заголовки отчёта и шаблон `ecg-functional-conclusion`;
- `lib/ecg-reference-links.ts`;
- куски препроцессинга: приведение к JPEG/PNG и компрессия. Маску краёв для ЭКГ не включать по умолчанию.

Оставить в production и не тащить:

- `lib/openrouter.ts` целиком, биллинг, auth, пациентскую базу, DICOM-стек, радиологический system prompt как «ECG reasoning»;
- `app/api/analyze/ecg/route.ts` как образец контракта;
- USB-модуль как источник 12-lead raw;
- деплой, nginx, Docker Doctor Opus.

Новый проект должен говорить с vision-моделью своим клиентом. Структурированные измерения из текста появятся только если их явно вынуть в объект из ТЗ; сейчас модель их не отдаёт отдельными полями, и пустые поля заполнять нельзя.

## 9. Следствие для архитектуры

Канал B из ТЗ в Doctor Opus уже есть как независимый image→vision→текст. Его можно перенести, не смешивая с ансамблем 531.

Канала raw ECG и канала 531 CSV в Doctor Opus нет. Их источник — `ecg_web_up` и будущий экстрактор.

Диджитайзер картинки в сигнал не реализован. Архитектурно для него места ещё нет, и в первой версии его делать не требуется.
